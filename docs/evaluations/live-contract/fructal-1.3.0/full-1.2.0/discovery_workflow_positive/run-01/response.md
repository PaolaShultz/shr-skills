**Give each refund request one dashboard record that customers, Finance, and Support can follow.** Finance can keep approving by email. The dashboard should show who owns the next action and what happens if submission, email delivery, or payment times out.

1. **Submit once.** Show the order, amount, reason, and “Finance approval required” before the customer selects **Request refund**. Save the entered details and a stable submission key before sending. The server uses that key to create or return one request. If the response times out, show **Checking submission** and recover the same request by key, even after a reload.
2. **Hand off to Finance.** Once the request is saved, show its ID and **Awaiting finance approval · Owner: Finance**. Send Finance the same ID and refund details. Record the authorized approver’s email decision against that request. Repeated replies have one effect. If email delivery fails, give the Finance queue a resend action on the existing request.
3. **Track the money separately from the decision.** A decline closes the request and gives the customer a reason. Approval moves it to **Processing refund**. If payment confirmation times out, show **Checking payment** and assign recovery to the payment operations team. They check the processor using the same payment reference before any retry. Show **Refunded** only after confirmation.
4. **Make ownership visible to Support.** Let Support look up the request by ID or order and see its current owner, last confirmed event, and next action. A handoff assigns the new owner and records the change together. Customers can reopen the same request to check progress without re-entering details.

Verify one payment, a visible recovery owner at every step, and status updates that customers can follow by keyboard and screen reader.
