Give each refund request **one durable ID, one current owner, and one visible next action**. Finance approval remains mandatory before money moves. Finance can still start from email, and customers and Support can follow the request in the dashboard.

1. **Submit once.** Show the amount and explain that Finance will review it. Give this submission a unique key before sending it. The server uses that key to create the request once and returns the same request ID on every retry. If the response times out, preserve the entered details and show “Checking whether your request was received.” Reopening the dashboard resumes that check.
2. **Hand off to Finance.** When the request is recorded, show the customer a receipt with its ID and “Awaiting Finance review.” Assign the Finance queue as owner immediately. The email carries the same ID and links to the request. If email delivery fails, the request stays in the queue and the notification can be retried. When a reviewer claims it, Support sees the reviewer’s name and next action.
3. **Record the decision.** An authorized reviewer confirms the amount and approves or declines the request. Record who decided and when. Reopening an old email shows the current decision. A decline closes the request with a customer-visible explanation. Approval hands ownership to the team responsible for issuing the refund, and the dashboard shows “Approved · payment pending.”
4. **Resolve payment uncertainty.** Use the request ID as a stable reference when issuing the refund. If payment times out, the payment owner checks the provider’s status before retrying. While the outcome is unknown, Support sees who is checking it and the customer sees “Confirming payment.” Mark the request “Refunded” only after confirmation.

**Verification before rollout.** Drop the submission response after the server saves it, then refresh and retry concurrently. Expect one ID and one Finance queue entry. Fail email delivery and confirm Finance can still claim the request. Have two reviewers act from the same email and confirm only one decision takes effect. Simulate a payment timeout after the provider accepts the refund and verify one payment, a visible recovery owner, and no change to another request for the same order. Check that customers and reviewers can complete their steps by keyboard and that a screen reader announces status changes.
