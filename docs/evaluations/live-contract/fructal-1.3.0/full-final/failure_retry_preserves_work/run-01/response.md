You identified scanning as mandatory and reported that a timeout and retry erase the title, file selection, return location, and request identity. The fixture records only `state=blocked`. The proposal assumes policy permits a receipt while files are held for scanning. Confirm which downstream action requires a clean scan and where pending files may be stored, for how long, and by whom they may be accessed.

**Proposed flow**

1. **Before sending**, assign the draft a stable request ID. Preserve the title, return location, and an ordered list of selected files with each file’s upload status. Keep this context within permitted storage. Submit commits the user’s intent once under that ID.
2. **If the connection times out**, keep the form in place and show “Checking whether your request was received.” Look up the same ID before retrying. If received, show its current status. If incomplete, resume only missing uploads under that ID. If the status service is unavailable, keep the outcome pending and offer “Check again.” The server must recognize repeated or concurrent submissions under that ID as one request.
3. **While scanning**, keep files isolated and the downstream action gated. The service retries temporary scan failures and assigns persistent failures to a support owner visible on the request. If a file needs replacement, identify it and offer a replacement control beside it. Preserve the title, other files, and return location. Release the request once all current files pass.
4. **On return or cancellation**, reopen the same request at its saved position. If an interruption revoked access to a local file that never finished uploading, name that file and ask the user to reselect only it. Leaving the page keeps a received request pending. An explicit cancellation records the outcome under the same ID. If completion races with cancellation, display the outcome the service actually committed.
