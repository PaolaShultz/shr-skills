Give each refund request **one tracking number from submission through payout**. The customer can use it to check a timed-out submission, Finance can use it to record a decision, and Support can use it to see who owes the next action.

1. **Submit once.** Before the customer submits, show the payment, refund amount, and requirement for Finance approval. Save the entered details and assign the attempt a stable ID. The server creates one request for that ID and returns the same tracking number on every retry. If the response times out, the dashboard shows “Checking whether your request was received” and looks it up. Any retry uses the original ID.
2. **Give Finance ownership at intake.** As soon as the request is recorded, show the customer “Received · Awaiting Finance approval.” Assign it to the Finance queue and email Finance a link to the record. The queue owns the next action until a reviewer claims it, at which point Support sees the reviewer’s name. A failed email stays visible for retry while the request remains in the queue.
3. **Record the decision before moving money.** An authorized Finance reviewer sees the payment and amount, then explicitly approves or declines. A decline closes the request and gives the customer a reason. Approval hands the request to payout processing. If the payout response times out, show “Confirming payout” and assign recovery to the payments team. They check the processor’s status before any replay and use the same payout ID for a supported retry.
4. **Make handoffs visible.** On the same record, show Support the current owner, next action, last update, and decision history. Show customers the status and any action they need to take. Mark the refund complete when the processor confirms it.

**Assumption:** Finance approval is mandatory. The request describes email as the current channel. If policy also requires the decision itself to happen by email, attach the authorized reviewer’s explicit email decision to the same record and apply the same payout gate.

**Verification plan:** Drop the submission response after the server saves it, then retry concurrently and reopen the dashboard. Check that the details survive and every attempt resolves to one tracking number. Simulate failed email delivery, reviewer reassignment, and an interrupted review, and have Support identify the owner and next action at each point. Exercise approval, decline, cancellation where permitted, and a payout timeout. Verify that only an approved request can produce a payout, at most one payout occurs, and unrelated refunds retain their state. Check that a keyboard and screen-reader user can submit, recover after timeout, and read the resulting status.
