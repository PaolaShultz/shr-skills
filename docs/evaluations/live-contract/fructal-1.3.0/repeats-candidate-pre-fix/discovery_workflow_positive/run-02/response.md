Give each refund request **one dashboard record and one reference number** from submission through payout. Finance approval remains mandatory before money moves. The proposal keeps email as Finance’s entry point and uses the dashboard to show who owns the next action.

1. **Submit once.** Show the amount and the Finance approval requirement before the customer selects **Request refund**. Give that submission a stable identifier before sending it. The server uses the identifier to create or retrieve one request, even if two submissions arrive together.
2. **Recover after a timeout.** Keep the entered details and show **Checking whether your request was received**. Check by the same identifier. If the request exists, open its receipt. If submission needs to be retried, reuse the identifier. Returning to the dashboard should resume this check without asking the customer to re-enter the request.
3. **Hand off to Finance.** As soon as the request is recorded, show the customer their reference and **Awaiting Finance approval**. Assign the next action to the Finance queue and email a link to the same record. When a reviewer claims it, Support sees their name, the next action, and when ownership changed. If email delivery fails, the request stays visible in the queue.
4. **Record the decision and follow the money.** An authorized reviewer confirms the amount and approves or declines. Record that decision once, including who made it and when. A decline closes the request with a customer-visible explanation. Approval moves it to **Processing refund**, with a designated payout owner. If payout times out, that owner checks the payment provider’s status before any retry. Show **Refund issued** only after confirmation.

**Verification plan.** Walk one approval and one decline through the flow. Drop the submission response after the server saves the request, then refresh and retry concurrently. Expect one reference, one Finance queue entry, and the original details. Also test a lost email, two reviewers acting at once, and a payout timeout. Verify that Support can identify the owner and next action at each handoff, that at most one payout occurs, and that customers using a keyboard or screen reader can find the receipt and hear status changes.
