**Save a private draft before reauthentication interrupts the form.** Build an authenticated, server-side draft tied to the account and form instance. On the shared device, keep sensitive entries only in the active page’s memory. The user supplies both requirements and reports the loss. The fixture records only `state=blocked`, so it does not establish what currently causes the loss.

1. **While the user edits**, save changes to the draft while the session is valid. Include the current step and field so the user can resume in place. Show “Saving…” until the server acknowledges that revision. If saving fails, show “Changes since the last save are unsaved” beside a keyboard-accessible **Retry save** action. Keep sensitive values out of browser storage, cached responses, URLs, and logs.
2. **When reauthentication is due**, lock the form immediately, remove its contents from view and from the accessibility tree, and enforce the authentication gate on the server. Use a sign-in flow that keeps the locked page alive so its latest unsaved edits can stay in memory. The lock must take effect even if a save is in flight.
3. **When the same user returns**, check which revision the server received before retrying an interrupted save. Apply remaining in-memory edits once. If another tab changed the draft, preserve both versions for the user to resolve. Restore the step and field, move focus there, and announce the recovery. Submission still requires an explicit **Submit** action.
4. **If sign-in fails or is canceled**, keep the form locked and offer **Retry sign-in** or **Leave this device**. Leaving, signing out, or switching accounts clears the page’s sensitive memory. A different account sees none of the draft. If the page closes or reloads, the original user can recover the last server-confirmed revision after signing in. Explain before leaving when newer edits exist only on this device.

**Policy decision.** The supplied policy covers local storage. The data owner still needs to establish whether server-side drafts are permitted, who may access them, and when they expire or are deleted. If server retention is prohibited too, same-page recovery using memory remains possible, but closing the page loses those edits.

**Verification plan.** Force expiry mid-field, during a failed save, and after the server accepts a save but before its acknowledgement arrives. Check that the gate takes effect on time, the same account recovers the correct values and position, and retries neither duplicate edits nor submit the form. Exercise cancellation, account switching, reload, and concurrent edits. With a keyboard and screen reader, verify lock announcements, recovery controls, focus restoration, and that locked values cannot be read. Inspect browser storage and caches after exit, and confirm that another account’s drafts, unrelated forms, and previously submitted records remain untouched.

This is a proposed design. No changes were made or behavioral tests run.
