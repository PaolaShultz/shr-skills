**Proposed replacement:** Let the requester submit once and hand the decision to an approver. Keep the protected action blocked until an authorized approver approves the exact revision the requester submitted.

The approval requirement comes from your request. The fixture records only `state=blocked`. It does not identify the protected action, the authorized approver, or who currently owns the handoff. Those details need to be established before implementation. [workflow.txt](/tmp/fructal-eval-implement_capped_by_no_modification-01-muq9frvh/fixture/workflow.txt:1)

1. **Submit and hand off.** Before submission, show what approval will authorize. On submission, preserve the entered work in permitted storage and create one request with a stable ID. Show both parties the same status, the current owner, and the next action. If routing fails, give the requester a way to retry the handoff on that record.
2. **Decide or revise.** The approver can approve the submitted revision, return it for changes with a reason, or decline it. A return gives ownership back to the requester and reopens the saved work at the field needing attention. A revised submission requires a fresh decision. Declining closes the request and shows the requester why.
3. **Complete or recover.** Record approval against the revision before starting the protected action. Serialize cancellation and execution so that a cancellation accepted before execution prevents the action. If execution has already started, show its actual status. After a timeout, the execution service checks the outcome using the request ID before any retry. If the outcome remains unknown, keep it pending and identify who owns reconciliation.

**Verification plan.** Follow one request through approval and confirm that the protected action occurs exactly once. Repeat with an unauthorized approver, a returned revision and stale approval, a decline, a routing failure, a cancellation racing execution, and a timeout after the action succeeds. Reopen the request after interruption and verify its content, position, owner, and next step. Check that both parties can complete their steps by keyboard and receive status changes through a screen reader. Confirm that unrelated requests retain their content and state.
