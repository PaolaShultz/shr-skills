Give each refund request **one tracking number and one current owner** from submission through payout. Finance can keep reviewing requests from email. The dashboard should show the decision and next step, so support can answer “Who has this?” without tracing an email thread.

1. **Submit once.** Before submission, show the refund amount and explain that Finance must approve it before money moves. Give this submission a stable retry key. The server uses that key to create the request once and returns the same tracking number for repeat clicks or retries. If the response times out, preserve the entered details and show “Checking whether your request was received.” The dashboard checks by key and retries with that same key if needed.
2. **Put Finance in charge at receipt.** As soon as the request is saved, show the customer “Received · Awaiting Finance review” with the tracking number. Assign the request to the Finance queue and email a link to that same record. Support sees the queue, the named reviewer once claimed, and the next action. If email delivery fails, the request stays visible in the queue and Finance can resend the notification.
3. **Record the decision and transfer ownership together.** The email link opens the request for an authorized reviewer. Approval records who approved which amount and assigns the next action to Payments. A decline closes the request and shows the customer the reason. Reopening an old email shows the current decision. Repeated or simultaneous decisions can trigger only one handoff.
4. **Resolve uncertain payouts before retrying.** Payments uses the tracking number as a stable payout reference. If the payment service times out, show “Confirming payout” and keep Payments responsible for checking the outcome. Mark the refund complete only after confirmation. If the outcome cannot be established, route it to a Payments operator for reconciliation before another payout attempt.
