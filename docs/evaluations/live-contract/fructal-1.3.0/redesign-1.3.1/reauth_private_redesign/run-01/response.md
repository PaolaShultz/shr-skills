**Keep the form in memory and reauthenticate in the same tab.** The proposed flow locks the form when authentication expires and returns the same user to the field they were editing. Signing in unlocks editing. Submission still requires a separate, explicit action.

The request establishes both requirements and reports the loss of entered work. The fixture records only `state=blocked`, so the cause of the loss is unverified. This design assumes policy permits sensitive values in volatile memory while the tab is locked. The proposal requires an authentication flow that can complete while the form page stays loaded.

1. **Before and during the lock.** Tell the user before entry that closing or refreshing the tab clears the draft. On expiry, the form controller retains the values, current step, focused field, and cursor position in memory. It removes the form from view and from the accessibility tree, moves focus to the lock prompt, and announces “Form locked. Sign in to continue.” Sensitive values stay out of browser storage, caches, authentication requests, and logs.
2. **On return.** The authentication service verifies fresh credentials. The form controller checks that the verified account owns the draft before revealing any field. For a match, it restores the step, scroll position, and keyboard focus. For a different account, it keeps the draft concealed and offers another sign-in attempt without identifying the owner.
3. **On interruption.** A failed, canceled, or timed-out sign-in leaves the draft locked in the open tab, with **Try again** beside the message. A separate **Discard draft** action explains the loss and asks for confirmation. Sign-out clears the draft. Closing the tab, refreshing it, or losing the browser process ends this recovery path. If recovery across those events is required, the open policy question is whether an owner-bound server draft and a defined retention period are permitted.

**Verification plan.** Expire a session halfway through a populated form and again as the user selects Submit. Check that the server requires fresh authentication, signing in sends no submission, and a rejected submission is never replayed automatically. If a submission was already in flight, check its status before offering a retry. Exercise failed sign-in, cancellation, account mismatch, and successful retry using a keyboard and screen reader. Verify that locked fields cannot be read, the prompt announces each outcome, and the owner returns to the exact field with values intact. Inspect storage, caches, logs, and authentication traffic for a distinctive test value. Finally, test discard, sign-out, refresh, and Back on the shared device, and confirm that draft cleanup leaves unrelated forms and preferences intact.
