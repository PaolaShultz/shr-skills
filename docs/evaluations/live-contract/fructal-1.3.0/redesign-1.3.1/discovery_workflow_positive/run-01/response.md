Give each refund request **one reference number, one current owner, and one visible next action**. Finance approval stays mandatory before money moves. The proposal assumes finance can receive an email link and record its decision in the dashboard.

1. **Submit once.** Show the order, refund amount, and approval requirement before the customer confirms. Give that submission a stable identifier before sending it. The server uses the identifier to create the request once and return the same reference on every retry. If the response times out, keep the entered details and show “Checking whether your request was received.” Reopening the dashboard or selecting “Check status” resumes that same submission.
2. **Route to finance.** As soon as the request is recorded, show the customer its reference and “Awaiting finance approval.” Assign it to the finance queue and email finance a link to the record. Support sees the queue as owner until a reviewer claims it, then sees the reviewer’s name. If email delivery fails, the item is still in the queue and support can see that notification needs a retry.
3. **Record the decision and transfer ownership.** An authorized reviewer checks the amount and approves or declines on the record. A decline closes the request with a customer-facing reason. Approval transfers ownership to the payments team for processing. Use the same refund reference for payment retries. If the payment outcome is unclear, payments owns reconciliation and checks the processor’s status before attempting another payout.
4. **Make progress visible.** Customers see the status and whether they need to act. Support can look up the same reference to see the current owner, last action, and next step. Show “Refund issued” only after the processor confirms it.

**Verification plan.** Simulate timeouts both before and after the server records a submission, then retry from a reopened dashboard. Both cases should produce one request with the original details. Test a lost finance email, two reviewers acting at once, a decline, and a lost payment response. Check that support can identify the owner at each handoff, only an approved request can pay out, and a retry produces at most one payout. Also check keyboard and screen-reader access to status and recovery actions, and confirm that a separate legitimate refund still proceeds independently.
