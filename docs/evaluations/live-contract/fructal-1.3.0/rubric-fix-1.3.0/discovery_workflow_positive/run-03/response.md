Give each refund request one reference that the customer, Finance, and Support can follow from submission through payment. Finance approval remains mandatory before money moves. The flow below keeps email as Finance’s entry point.

1. **Submit once.** Show the order, refund amount, and approval requirement before the customer submits. Give that submission a stable identifier and preserve it with the entered details across refreshes. The server creates the request once and returns the same reference for repeat submissions with that identifier.
2. **Recover after a timeout.** Show “Checking whether your request was received” and provide a **Check status** action. Look up the submission by its identifier. If it was received, show its reference and status. If it still needs to be sent, retry with the same identifier. The customer can close the dashboard and resume without re-entering details.
3. **Hand the request to Finance.** Once received, show “Awaiting Finance approval,” assign it to the Finance queue, and email Finance a link to the record. When a reviewer claims it, Support sees the reviewer’s name, the next action, and when ownership changed. If email delivery fails, the request stays visible in the Finance queue and the notification can be retried. An authorized reviewer explicitly approves or declines against the displayed order and amount. Reopening the email shows the recorded decision.
4. **Track the refund through payment.** A decline closes the request with a customer-visible explanation. Approval transfers ownership to Payments. If the payment service times out, Payments owns reconciliation and checks the existing transaction before retrying with the same refund identifier. Mark the request “Refunded” only after confirmation. Support can look up the reference at every stage and tell the customer who acts next.

**Verification plan.** Drop the response both before and after the server saves a submission, then refresh and submit twice concurrently. Expect one request, one reference, and the original details. Delay the Finance email, reassign the reviewer, and repeat an approval. Check that Support sees the current owner throughout, a decline produces no payment, and an approval followed by a payment timeout produces at most one refund. Verify that a separate legitimate request remains independent and that customers can recover using a keyboard and hear status updates with a screen reader.

This is a proposed flow. The fixture records only `state=blocked`, so it does not establish where duplicates originate or whether the payment provider supports refund lookup and safe retries. If the provider cannot establish the outcome, Payments should retain ownership for manual reconciliation before another payout attempt. No changes were made or external services accessed.
