Give each refund request one durable reference. Use it in the customer dashboard, the finance email, and support’s view so everyone can find the same request, see who owns the next step, and recover after a timeout. Finance approval remains a prerequisite for issuing money.

1. **Submit once.** The dashboard shows the amount and purchase, explains that Finance must approve the refund, and saves the draft with a stable submission key. When the customer submits, the server uses that key to create or return the same request, even if two submissions arrive together. If the response times out, the dashboard preserves the entries and offers **Check status**. Any retry uses the original key.
2. **Hand off to Finance.** As soon as the server accepts the request, the customer sees its reference and **Awaiting finance review**. The finance queue owns it immediately. The email includes the reference and a link to the request, where an authorized reviewer claims it and records approval or decline. If the email is delayed or lost, the request stays visible in the queue. Support can see the queue or named reviewer, the last update, and the next action.
3. **Track the money separately from the decision.** Approval moves the request to **Processing refund**. The payment service uses the request reference as its retry key and marks the refund **Issued** only after confirmation. If the payment outcome is unclear, payment operations owns reconciliation and checks the provider’s status before another attempt. A decline closes the request and shows the customer the reason.

This assumes Finance can record its decision through a link from email. If policy requires an email reply, use the same reference to attach the authorized reviewer’s reply to the request and record the decision once.
