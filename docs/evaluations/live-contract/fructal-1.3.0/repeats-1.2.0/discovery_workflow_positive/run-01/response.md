**Give each refund request one reference that follows it from the dashboard through finance’s email decision.** Customers can use that reference to recover after a timeout, and support can use it to see who owes the next action. Finance approval is required. This proposal assumes email remains the approval channel.

1. **Submit once.** Save the customer’s entries and assign the draft a stable reference before submission. Label the action **Submit for finance review** so the customer knows what it does. The server should create at most one request for that reference, even if two submissions arrive together.
2. **Recover in place.** After a timeout, keep the entries on screen and offer **Check request status**. If the server accepted the request, show its receipt and current status. If it confirms the request was never accepted, offer **Retry** using the same reference. While the outcome is unknown, keep the reference visible and let the customer leave and return.
3. **Make the finance handoff explicit.** Send the review email with the reference, amount, and reason. Show support the owner, next action, and last update on the request. For example, **Support · Resolve email delivery** means support owns a failed handoff. Once delivery is confirmed, **Finance queue · Review request** identifies the owner until a reviewer claims it.
4. **Close the loop.** Match the authorized reviewer’s email decision to the reference and record it once. A decline closes the request with a customer-visible reason. Approval passes ownership to the refund-processing team. Show **Refund issued** only after processing is confirmed. If processing times out, that team checks the payment outcome before retrying.

**Verification plan.** Simulate a timeout both before and after the server accepts a submission, then retry from two tabs. Both paths should produce one request with the original entries. Exercise failed email delivery, reviewer handoff, approval, decline, a repeated reply, and an interrupted payout. At each step, ask support to identify the owner and next action from the record alone. Verify that a customer returning by keyboard or screen reader can find the reference, hear the status update, and recover without re-entering details.
